# ADR-0014: 대본 세션은 beat·text·subject 세 필드만 출력한다

- 상태: 승인
- 날짜: 2026-08-10
- 관련 스펙: specs/01-script-template.md, specs/02-beat-schema.md, specs/03-visual-rules.md, specs/05-pipeline.md

## 맥락

`[1. script]`의 산출물은 스펙 02의 씬 객체 배열이다. 씬 하나에 `scene_id`·`beat`·`text`·
`est_start`·`est_end`·`emphasis`·`subject`·`camera`·`motion`·`notes` 열 개 필드가 있다.

이걸 전부 세션이 출력하게 하면 두 가지가 깨진다.

**첫째, 산술을 LLM에 맡기게 된다.** `est_start`/`est_end`는 앞 씬의 누적 시간이라 26줄이면
52번의 덧셈이다. 한 줄만 어긋나도 뒤가 전부 밀리고, 스펙 01의 "발상을 뒤집습니다는 44~54초"
검증이 무의미해진다 — 세션이 타임스탬프를 직접 쓰면 규칙에 맞는 숫자를 적어놓고 실제 분량은
다르게 쓸 수 있기 때문이다.

**둘째, 룰 테이블이 무력해진다.** 스펙 03은 "이미지 프롬프트·오버레이·전환은 이 테이블로
결정한다. LLM이나 개발자가 임의 판단하지 않는다"고 못박고 있고, ADR-0001도 "LLM의 창의적
판단은 `subject`와 대본 내용에만 허용한다"고 한다. `camera`를 세션이 고르면 이 둘을 어긴다.

## 결정

세션은 `beat`·`text`·`subject` 세 필드만 출력한다. 나머지는 오케스트레이터가 채운다.

| 필드 | 주체 | 방법 |
|---|---|---|
| `text`·`beat`·`subject` | 세션 | 창의적 판단 (ADR-0001) |
| `scene_id` | 코드 | 배열 순서 |
| `est_start`·`est_end` | 코드 | 줄의 글자 수 ÷ 명목 발화 속도 5.85자/초 |
| `camera` | 코드 | 스펙 03 비트별 기본값 |
| `emphasis` | 코드 | 숫자 비트 → 본문 첫 숫자를 대형 빨간 텍스트로 |
| `motion` | 코드 | 전부 `kenburns` |

명목 속도 5.85자/초는 원본 3편 실측(5.396~6.217)의 중앙 부근이다. 545~575자를 넣으면
93~98초가 나와 스펙 01의 90~102초 안에 떨어진다. 세션은 타임스탬프를 못 쓰는 대신
**"발상을 뒤집습니다" 앞 누적 글자 수를 260~310자로 맞추라**는 지시를 받는다. 이게 그 문장을
44~54초에 놓는 유일한 수단이고, 실제 분량과 타이밍이 분리될 수 없게 만든다.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| 세션이 씬 객체 전체를 출력 | 단계 코드가 얇아짐 | 타임스탬프 산술 오류, 룰 테이블 우회 | 스펙 03·ADR-0001 위반 |
| 세션이 텍스트만 출력하고 비트는 별도 분류 호출 | 역할 분리 명확 | 호출 2회, 비트 정보를 버렸다 복원 | ADR-0003이 이미 기각 |
| `est_*`를 세션이 쓰되 코드가 재계산해 대조 | 세션의 의도 확인 가능 | 불일치 시 처리 규칙이 또 필요 | 얻는 것 없이 계약만 커짐 |

## 결과

- `[1. script]`의 세션 출력 계약은 `{"scenes": [{"beat", "text", "subject"}]}` 하나다
- `motion`이 항상 `kenburns`라 `kling`은 이 단계에서 선택되지 않는다. 유체 모션 판단은
  이미지가 나온 뒤 `[7. motion]`에서 하는 편이 근거가 많다 (ADR-0006의 씬당 상한은 유지)
- 스펙 03에 비트별 오버레이 enum이 아직 없어(슬라이스 1에서 확인) `emphasis.type`은 숫자
  비트의 `big_red_text` 하나만 쓴다. 나머지 비트의 오버레이는 채우지 않는다
- 되돌릴 조건: 실측 TTS 길이가 추정과 씬당 ±1.5초를 넘게 벌어지면(스펙 05) 명목 속도를
  고정 상수가 아니라 비트별·문장부호별 가중으로 바꾸는 안을 재검토
