# ADR-0017: 1부와 2부의 경계를 읽기 전용 계약으로 동결하고, 2부 산출물은 run 디렉터리에만 쓴다

- 상태: 승인
- 날짜: 2026-08-11
- 관련 스펙: specs/05-pipeline.md, specs/02-beat-schema.md, specs/06-topic-research.md
- 관계: ADR-0009(인간 게이트), ADR-0011(단계 I/O 계약)의 경계를 1부↔2부로 확장. ADR-0013(씬=자막 줄) 유지

## 맥락

1부(대본 생산)와 2부(영상 생산)를 **각각 독립적으로 계속 개발**하려 한다. 근거는 셋이다.

1. **최적화 성격이 다르다.** 1부는 한계비용 0의 텍스트 반복(프롬프트·검증기·사실 근거)이고,
   2부는 편당 ~$7의 렌더 반복(시각 품질·API 실패·FFmpeg)이다. specs/05의 비용 기준선이
   이 비대칭을 이미 전제한다 — 1부는 "완전 자동, 일 1~5개", 2부는 "go 승인분만".
2. **모든 대본을 영상으로 만들지 않는다.** ADR-0009가 정한 순서가 그대로다 —
   1부 결과 여러 개 → 사람 검토 → 승인분만 2부. 초기에는 사람이 눈으로 고른다.
3. **고치는 자리가 다르다.** 대본이 마음에 안 들면 1부를, 이미지가 마음에 안 들면 2부를
   따로 손대야 한다. 지금은 그게 안 된다.

**안 되는 이유가 스펙에 있다. 경계가 단방향이 아니다.**

```
specs/02-beat-schema.md:48
  `est_start`/`est_end`: TTS 생성 전 추정치. TTS 후 실측값으로 갱신되며, 갱신 후 필드명은 `start`/`end`.

specs/05-pipeline.md:26
  → [3. tts+sync]   → narration.wav + timing.json + scenes.json 갱신
```

**2부의 첫 단계가 1부의 산출물을 제자리에서 고쳐 쓴다.** 결과는 세 가지다.

- 1부에서 대본을 다시 뽑으면(`[2] validate`의 재생성은 실제로 후보를 3개까지 만든다)
  2부가 써넣은 실측 타임스탬프가 덮인다
- 두 개발 라인이 같은 파일에 쓰므로 병렬 작업 시 충돌한다
- "이 영상이 어느 대본으로 만들어졌는가"를 파일 내용 비교 말고는 확인할 수 없다

**2부 산출물의 저장 위치도 정해진 적이 없다.** specs/05는 `narration.wav`, `prompts.json`,
`images/{scene_id}.png`, `clips/{scene_id}.mp4`, `timeline.mp4`, `final.mp4`, `report.md`를
나열만 하고 경로를 말하지 않는다. `.gitignore`는 `runs/*`만 제외하므로, 이대로 두면
`topics/{slug}/` 아래에 수백 MB의 바이너리가 커밋될 수 있다.

한편 **2부 개발에 필요한 입력은 이미 확보돼 있다.** 검증을 통과한 `06-script.json`이 2개 있다
(피사 25씬/97.4초, 후버댐 27씬/97.3초). 경계만 굳히면 2부는 1부 코드를 한 줄도 보지 않고
이 두 파일만으로 끝까지 개발할 수 있다.

## 결정

**`topics/{slug}/06-script.json`을 1부의 최종 산출물이자 2부의 읽기 전용 입력으로 동결한다.
2부는 이 파일을 절대 수정하지 않고, 자신의 모든 산출물을 `runs/{run_id}/` 아래에만 쓴다.**

경계면은 파일 **두 개**다. 2부는 그 밖의 1부 산출물(`01`~`05`, `research.json`)에 의존하지 않는다.

| 파일 | 역할 | 쓰는 쪽 | 읽는 쪽 |
|---|---|---|---|
| `topics/{slug}/06-script.json` | 씬 계약 (specs/05 핵심 계약 = scenes.json) | 1부 `[2]` | 2부 전 단계 |
| `topics/{slug}/judgment/human.json` | 게이트. `decision: go`일 때만 2부 진입 | 사람 | 2부 진입점 |

- **게이트는 `judgment/human.json`이다.** 스키마는 specs/07이 이미 정의했다(`decision`, `reason_code`,
  `scores`, `judged_at`). `STATUS.md`는 사람이 읽는 요약으로 남긴다 — ADR-0011이 세운
  "사람용 마크다운 / 기계용 JSON" 분리를 그대로 따른다.
- **`[3. tts+sync]`는 `scenes.json`을 갱신하지 않는다.** 실측 타임스탬프를 담은
  `runs/{run_id}/scenes.timed.json`을 **새로 쓴다.** 필드명이 `start`/`end`로 바뀌는 것은
  specs/02 그대로다 — 다만 그것이 *같은 파일의 갱신*이 아니라 *다른 파일*임을 명확히 한다.
  `est_*`는 추정, `start`/`end`는 실측이라는 구분이 파일 단위로 보인다.
- **2부 산출물은 전부 `runs/{run_id}/` 아래**에 둔다. `runs/*`가 이미 `.gitignore` 대상이라
  미디어 바이너리가 저장소에 섞이지 않는다.
- **`06-script.json`에는 계보를 적는다.** 이미 있는 `run_id`가 그 역할을 한다.
  2부 산출물은 같은 `run_id`의 run 디렉터리에 놓이므로 어느 대본에서 나왔는지가 경로로 드러난다.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| 현행 유지 — `[3]`이 `scenes.json`을 제자리 갱신 | 타임스탬프가 한 파일에 모임, 스펙 수정 불필요 | 1부 재생성이 2부 작업물을 덮음. 두 라인이 같은 파일에 씀 | **이 ADR의 목적인 독립 개발이 성립하지 않는다.** `[2] validate`가 후보를 3개까지 재생성하므로 실제로 덮어쓰기가 일어난다 |
| 2부가 `06-script.json`을 자기 디렉터리로 복사한 뒤 사본을 갱신 | 원본 불변, 코드 변경 최소 | 사본이 원본과 어긋나도 감지할 수 없음 | 계약이 아니라 관행이 된다. 어긋남을 검증할 수단이 없어 "이 영상이 어느 대본인가"가 다시 불확실해진다 |
| 2부 산출물을 `topics/{slug}/` 아래에 둠 | 한 폴더에서 대본과 결과물을 같이 봄 | mp4·png·wav가 git에 들어감 | `.gitignore`가 `runs/*`만 제외한다. 편당 수백 MB가 커밋되고, ADR-0011의 "사람 검토용 폴더에 기계 파일을 섞지 않는다"를 위반한다 |
| 게이트를 `STATUS.md` 파싱으로 판정 | 새 파일이 없음 | 마크다운 파싱은 형식이 조금만 흔들려도 깨진다 | specs/07이 `judgment/human.json`을 이미 정의해 뒀다. 있는 계약을 두고 마크다운을 파싱할 이유가 없다 |
| 경계를 `runs/{run_id}/script.json`(기계 계약)으로 옮김 | ADR-0011의 "계약은 run 디렉터리" 원칙과 일치 | 사람이 검토하는 대상이 run 디렉터리로 이동 | specs/06이 `06-script.json`을 토픽 패키지의 산출물로 정의했고, ADR-0009의 인간 게이트가 검토하는 대상이 바로 이 패키지다. 사람이 보고 고르는 파일이므로 패키지에 남아야 한다 |

## 결과

- **2부는 `06-script.json` 2개(피사·후버댐)만으로 즉시 착수할 수 있다.** 1부 코드·1부 진행 상황과
  무관하게 개발·테스트된다. 픽스처가 실물이라 별도 제작이 필요 없다
- **1부는 2부를 신경 쓰지 않고 대본을 몇 번이든 재생성할 수 있다.** 2부 산출물을 건드리지 않는다
- 2부 단계 실패 시 재실행 범위가 run 디렉터리 안으로 한정된다 (specs/05 실패 정책과 일치)
- `[3. tts+sync]`가 `scenes.json`을 갱신한다는 서술이 specs/02·05 두 곳에서 바뀐다 (아래 diff)
- 미디어 바이너리가 저장소에 들어오지 않는다
- **되돌릴 조건**: 2부가 `06-script.json` 외의 1부 산출물(예: 이미지 프롬프트를 위해 `04-factsheet.json`의
  사실 원문)을 실제로 필요로 하는 일이 반복되면, 경계면 파일 목록을 늘리는 것을 재검토한다.
  경계면이 3개를 넘어가면 "인터페이스만 맞추고 독립"이 성립하지 않으므로, 그때는 1부가
  2부용 요약 계약을 따로 내보내는 방안을 검토한다

## 승인 시 적용할 스펙 수정

### `specs/02-beat-schema.md`

```diff
-- `est_start`/`est_end`: TTS 생성 전 추정치. TTS 후 실측값으로 갱신되며, 갱신 후 필드명은 `start`/`end`.
+- `est_start`/`est_end`: TTS 생성 전 추정치. **이 값은 갱신되지 않는다** (ADR-0017).
+  `[3. tts+sync]`가 실측값을 `runs/{run_id}/scenes.timed.json`에 **새로 쓰며**, 그 파일에서
+  필드명은 `start`/`end`다. 추정(`est_*`)과 실측(`start`/`end`)은 파일 단위로 분리된다.
```
