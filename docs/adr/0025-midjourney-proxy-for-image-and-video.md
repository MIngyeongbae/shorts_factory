# ADR-0025: 이미지·영상 생성을 Midjourney 정액 구독 + 프록시로 옮긴다

- 상태: **승인** (2026-08-12, Standard $30 결제로 확정)
- 날짜: 2026-08-12
- 관련 스펙: specs/02-beat-schema.md, specs/03-visual-rules.md, specs/05-pipeline.md
- 관련 ADR: ADR-0005(NB2 선정 — **본 ADR이 탈락 사유를 번복한다**), ADR-0006(모션 하이브리드),
  ADR-0021(NB2 호출 경로 — 폴백으로 유지), ADR-0020(값의 출처는 하나), ADR-0001(룰 기반 연출),
  ADR-0017(편당 ~$7 기준선)

## 맥락

### 문제는 편당 단가가 아니라 손익분기다

specs/05의 비용 기준선은 편당 ~$7(이미지 ~$2.5 + Kling ~$4.5)이다. 이 수치 자체는 지켜지고
있다(ADR-0021 실측 $2.53~2.73). 문제는 **여기에 Claude 구독 30만원/월이 고정으로 얹힌다**는
것이다. 월 30편 기준으로 풀면:

| 항목 | 월 | 성격 |
|---|---|---|
| Claude 구독 | 30만원 | 고정 (축소 대상 아님 — 사람 결정) |
| 이미지 NB2 $2.63×30 | 11만원 | 변동 |
| Kling $4.5×30 | 19만원 | 변동 |
| ElevenLabs Creator | 3만원 | 고정 (대본 570자 → 월 200편 커버, 병목 아님) |
| **합계** | **63만원** | |

한국 쇼츠 RPM은 1,000뷰당 **15~60원**이다. 63만원을 광고 수익으로 회수하려면 RPM 30원
기준 **월 2,100만 뷰 = 편당 70만 뷰**가 필요하다. specs/05가 적어 둔 "편당 10만~180만 조회"
범위의 상단이다.

**변동비를 0으로 만들어도 손익분기는 편당 70만 → 47만 뷰로만 내려간다.** 그럼에도 이 결정을
하는 이유는 절감액 자체가 아니라 **편수를 늘릴 때 비용이 따라 오르지 않게 만드는 것**이다.
현행 구조에서는 편수를 두 배로 늘리면 변동비도 두 배가 되어 손익분기가 개선되지 않는다.

### ADR-0005의 "Midjourney: 공식 API 없음 → 자동화 불가"는 더 이상 사실이 아니다

ADR-0005는 Midjourney를 **자동화 불가**를 이유로 탈락시켰다. 공식 API가 없다는 사실은
2026-08 현재도 그대로다(Enterprise 대시보드 신청 기반 제한 접근만 존재). 그러나 프록시
경로가 성숙했다. GitHub 실사 결과:

| 프로젝트 | 언어 | ⭐ | 마지막 커밋 | 영상 | 웹앱 | 판정 |
|---|---|---|---|---|---|---|
| **trueai-org/midjourney-proxy** | C# | 806 | **2026-08-10** | **O** | **O** | 유일한 후보 |
| novicezk/midjourney-proxy | Java | 5,346 | 2025-08 | X | X | 1년 정체, 영상 없음 |
| erictik/midjourney-api | TS | 1,871 | 2026-07 | X | Discord만 | 영상 없음 |
| yokonsan / George-iam / ezioruan 등 | Py | <900 | 2023~2024 | X | X | 사망 |

`trueai-org`만 세 조건을 동시에 만족한다: **영상 생성 지원**, **MJ 공식 웹앱 경로 지원**
(Discord self-bot을 안 거친다), **REST API 노출**(파이썬에서 그대로 호출). ~~Windows 단독
실행 파일과 Docker 배포를 모두 제공한다.~~ → **Docker만 쓸 수 있다** (G1 실측).

이 프로젝트는 밴 회피를 문서에 정면으로 적어 뒀다 — 작업 간격 **30~180초**, 일일 **~200잡
상한**, 작업 시간대 설정(24시간 연속 금지), CloudFlare CAPTCHA 자동 처리, 계정 풀 로테이션.

### 처리량 — Standard 플랜이 병목을 어디에 두는가

MJ 공식 수치(David Holz 발표): **영상 1잡 = 이미지 잡의 8배 GPU 시간, 잡당 5초 클립 4개**.
실측 환산으로 이미지 1잡 ≈ 1 GPU분, SD 영상 1잡 ≈ **8 GPU분**.

플랜 비교(2026-08-12 결제 페이지 직접 확인):

| | Standard $30 | Pro $60 |
|---|---|---|
| Fast 시간 | 15h | 30h |
| Relax 무제한 | **이미지만** | 이미지 **+ SD 영상** |
| 동시 Fast 잡 | 이미지 3 / 영상 3 | 이미지 12 / 영상 6 |
| Stealth mode | **없음** | 있음 |

**이미지는 Relax로 돌리면 Fast 시간을 0 소모한다.** 따라서 Standard의 Fast 15h는 전부
영상에 쓸 수 있다:

| 편당 영상 씬 | Fast 소모/편 | Standard 월 상한 |
|---|---|---|
| **10씬 (ADR-0006 현행 상한)** | 80분 = 1.33h | **11편** |
| 5씬 | 40분 = 0.67h | 22편 |
| 3씬 | 24분 = 0.40h | 37편 |

Fast 시간 추가 구매는 $4/h이므로 초과분은 편당 $5.33 — **Kling의 $4.5보다 비싸다.**
top-up은 경로가 아니다. Standard→Pro 승급 손익분기는 차액 $30 ÷ $5.33 = **월 17편**이다.

### 밴 위험의 실제 크기

하루 1편 = **36잡/일**(이미지 26 + 영상 10)이다. 프록시가 권장하는 일일 상한 200잡의
**18%**, 커뮤니티에 보고된 밴 사례("하루 300 요청")의 **12%**다. 위험이 0은 아니지만,
이 볼륨은 상업적 대량 수집과 자릿수가 다르다.

**Midjourney ToS 위반이라는 사실은 바뀌지 않는다.** ToS는 "자동화 도구로 서비스에 접근·
상호작용하거나 Asset을 생성하는 것"을 명시적으로 금지하고, 정지 사유로 든다. 이 ADR은
그 위험을 모르고 지나가지 않기 위해 여기 적는다 — **사람이 위험을 인지하고 선택한 결정이다.**

## 결정

**세 가지를 한꺼번에 결정한다.**

### 1. 프로바이더를 Midjourney Standard($30/월) + `trueai-org/midjourney-proxy`로 전환한다

- **Standard로 시작한다.** Pro가 아닌 이유는 아래 "승인 게이트"가 아직 안 열렸기 때문이다.
  480p 업스케일이 ADR-0023 룩을 못 버티면 Pro $60은 그대로 날아간다. 승급 조건은 월 17편.
- **웹앱 경로를 쓴다.** Discord 경로는 self-bot이라 Discord ToS까지 이중 위반이고 밴 이력이
  더 공격적이다. 프록시가 웹앱 모드를 지원하므로 선택할 이유가 없다.
- **월간 결제.** 연간 20% 할인($288)은 밴 시 손실을 7배로 만든다. 정지 위험이 있는 계정에
  선불을 묶지 않는다.
- 프록시 설정: 잡 간격 30~180초, 일일 상한 200, 작업 시간대 제한 **전부 켠다.**
- **Docker 배포만 쓴다.** 초안은 "Windows 단독 실행 파일과 Docker 배포를 모두 제공한다"고
  적었는데 **이 PC에서 Windows 빌드가 안 돈다** — 아래 "G1 실측"의 배포 항목 참조.

### 2. 이미지는 Relax, 영상은 Fast로 강제 분리한다

이것이 구현의 필수 조건이다. 기본 모드가 Fast면 이미지 26잡이 26 GPU분을 갉아먹어
월 11편이 6편으로 떨어진다.

~~`[6]`이 만드는 모든 프롬프트에 **`--relax`를 무조건 붙인다.**~~ → **G1에서 정정.**
모드는 프롬프트 플래그가 아니라 **엔드포인트 URL 프리픽스로 고른다**:

| 용도 | 엔드포인트 |
|---|---|
| 이미지 | `POST /mj-relax/mj/submit/imagine` |
| 영상 | `POST /mj-fast/mj/submit/video` |

프록시가 `--relax`를 자동으로 붙여 준다(G1에서 `full_command` 끝에 `--relax` 확인).
어댑터가 프롬프트 문자열을 만질 필요가 없으므로 불변식이 더 단단해진다 — **프리픽스를
틀리면 잘못된 프롬프트가 아니라 아예 다른 엔드포인트가 된다.**

계정 쪽에도 잠금장치를 건다: `enableAutoSetRelax=true`, **`enableRelaxToFast`는 반드시 OFF**
(켜져 있으면 Relax 잡이 Fast로 넘어가 15시간을 태운다).

### 3. `motion` enum에 `mj_video`를 추가하고 `kling`은 남긴다

`kling`을 지우지 않는 이유는 ADR-0006의 하이브리드 판단(유체 모션이 서사상 필요한 씬)이
그대로 유효하고, MJ가 밴당하면 돌아갈 곳이 필요하기 때문이다. 강등 사다리는
**`mj_video` → `kenburns` → `static`**으로, 지금 `stages/motion.py`에 있는 구조를 그대로 쓴다.

### 구현 중 확인 사항

ADR-0021이 $0.101짜리 실호출 한 번으로 여섯 항목을 확정한 것과 같은 방식이다.

| # | 확인할 것 | 상태 | 실패 시 |
|---|---|---|---|
| **G1** | 프록시가 웹앱 모드로 붙어 이미지 1잡·영상 1잡이 실제로 나온다 | **통과 (2026-08-12)** | 이 ADR 폐기, 현행 유지 |
| **G3** | `--sref`로 씬 간 룩 일관성이 스타일 앵커 3장 수준 이상 나온다 | **통과 (2026-08-12) — 단 결론이 반대다.** `--sref`를 **쓰지 않을 때** 일관성과 마감이 모두 낫다. 아래 "G3 실측" | 이미지는 NB2 유지(ADR-0021 경로 생존), MJ는 앵커 제작 용도만 |

### G2(480p 업스케일 화질 검증)는 폐기했다 — 그리고 그 위험은 남는다

초안에는 **"480p·24fps → 1080×1920·30fps 업스케일에서 ADR-0023 룩이 버티는가"** 를
승인 게이트로 뒀다. **2026-08-12에 사람이 폐기했다.** 별도 탐침 단계를 두지 않고 첫
실제 편에서 판단한다.

**이 판단으로 받아들인 위험을 여기 적는다.** MJ V1 영상은 480p / 24fps / 무음 / 5초이고,
최종 출력까지 **2.25배 업스케일 + 24→30fps 변환**이 붙는다. 지난 세션이 `format=gbrp`
하나로 잡아낸 종류 — **순수 계산으로는 안 잡히고 눈으로만 보인다.**

게이트를 없앤 것이지 위험을 없앤 것이 아니다. G1에서 영상 1개가 나오는 순간 480p는
어차피 눈에 보이므로, 폐기의 실질은 **"그걸 이유로 진행을 막지 않는다"** 이다.
화질이 못 버틴다고 판명되면 아래 되돌릴 조건의 RunPod / Kling 경로로 간다 —
**두 경로 모두 과금이라 "변동비 0"이라는 이 ADR의 목적이 깨진다.**

## G1 실측 (2026-08-12, 이미지 3잡 + 영상 2잡)

**G1 통과.** 산출물은 `runs/20260812-g1-mj-probe/`에 있다(gitignore 대상).

### 처리량 — 추정이 아니라 계정 카운터로 확정됐다

| | 이미지 | 영상 |
|---|---|---|
| 해상도 | **816 × 1456** | **464 × 832** |
| 잡당 산출 | **4장** (`0_0`~`0_3`) | 4개 |
| 모드 | RELAX | FAST |
| **Fast 소모** | **0분** | **정확히 8.0분 (480초)** |
| 소요 | 45초 | 43~76초 |
| 기타 | MJ v8.2, `batch_size=4` | h264 / **24fps** / **5.21초** / 125프레임 / 무음 |

`officialFastRemaining`이 `54000 → 53520 → 53040`초로 정확히 480씩 줄었다. 맥락 절의
"영상 1잡 = 8 GPU분"이 **실측으로 확정**됐고, 따라서 **월 11.2편**도 확정이다.

**과금 모델 (`[11] report`가 쓸 값):**

| 값 | 의미 |
|---|---|
| `officialFastRemaining` | 잔여 Fast **초**. 900분 = 54,000초에서 시작 |
| `credits_total` | 1000 크레딧 = 1초. Fast 풀 |
| `relax_credits` | **음수로 내려간다** — Relax는 무제한이라 한도가 아니라 사용량 기록이다 |

Fast와 Relax는 **별도 풀**이다. 이미지 3잡이 `relax_credits`를 −135,000(=135초)만 움직였고
Fast는 1초도 건드리지 않았다.

### 인증 — 액세스 토큰만으로는 안 된다

`isOfficial` 계정은 `userToken` 필드 하나만 쓴다(`cookie` 필드는 UI에 없다). 여기에
**쿠키 문자열 전체**를 넣어야 한다:

```
__Host-Midjourney.AuthUserTokenV3_i=<액세스>; __Host-Midjourney.AuthUserTokenV3_r=<리프레시>
```

- **액세스 토큰 값만 넣으면 401이 난다.** 프록시가 이 값을 `Cookie:` 헤더에 그대로 넣으므로
  `이름=값` 형태가 아니면 MJ가 읽지 못한다
- **액세스 토큰의 수명은 60분이다** (JWT `exp` − `iat` = 3600). DevTools가 보여주는 쿠키
  만료일(약 30일)은 쿠키 그릇의 것이지 JWT의 것이 아니다
- **리프레시 토큰을 같이 넣는 것이 이 계약의 핵심이다.** 액세스 토큰 값만 넣었다면
  60분 뒤에 죽고 재시작하면 무조건 죽는다

**자동 갱신은 확정됐다 (2026-08-12 13:02).** 초안 시점에는 "프록시가 갱신 중"과 "MJ에
유예 시간이 있다"를 구별하지 못했는데, 두 관측이 갈랐다:

| 시험 | 결과 |
|---|---|
| 만료 **86분** 후 인증 | **통과** (587ms). 유예 시간으로는 설명 불가 |
| **컨테이너 재시작 후** 인증 | **통과** (5,633ms — 컨텍스트 재초기화) |

두 번째가 결정적이다. **DB에는 만료된 액세스 토큰이 그대로 있는데** 거기서 새로 부팅해
붙었다 — 프록시가 **리프레시 토큰만으로 부트스트랩**한다는 뜻이다. 갱신본은 브라우저
컨텍스트(메모리)에만 있고 DB에 쓰이지 않지만, DB에 리프레시 토큰이 있으므로 재부팅이
안전하다.

**따라서 `[0] token` 수확 단계는 만들지 않는다.** Firebase 경로는 되돌릴 조건에만 남긴다.

MJ 계정이 Google/Discord OAuth만 지원하므로 **`loginAccount`/`loginPassword` 자동 로그인
경로는 쓸 수 없다.** `AutoLoginRequest`가 `login2fa`(TOTP 시드)를 필수로 요구하는데,
휴대폰 인증(SMS/프롬프트) 사용자는 넘겨줄 시드가 없다. 그 필드는 Discord 계정용이다.

### 배포 — Windows 단독 실행 파일은 이 PC에서 안 돈다

`v11.10.4`·`v11.10.3` **둘 다 동일하게 크래시**한다(난독화 심볼명만 다름):

```
System.TypeInitializationException: '<Module>'
 → Marshal.GetDelegateForFunctionPointer(IntPtr ptr, Type t)
 → ArgumentNullException: Value cannot be null. (Parameter 'ptr')
```

버전 회귀가 아니라 환경 문제이고 **보안 소프트웨어 차단도 아니다**(ASR 규칙 없음,
Controlled Folder Access 꺼짐, Defender 탐지 0건, .NET 8.0.14 설치됨). 난독화 코드라
더 파도 얻을 것이 없어 **Docker(Linux 컨테이너)로 우회했다.**

### 필수 설정 2건 — 이것 없이는 파이프라인이 성립하지 않는다

**① Redis (업스트림 버그 우회)**

`EnableRedis=False`인데도 `CounterHelper`가 `RedisHelper`를 무조건 호출한다. 그 결과
`AdminController.Accounts()`·`Users()`·`HomeController.Info()`가 **전부 500으로 죽는다** —
계정 목록 화면이 실제로 안 뜬다. 별도 Redis 컨테이너를 붙이고 `redisConnectionString`을
설정해 해결했다.

**② `ImageStorageType = LOCAL` (Cloudflare 우회)**

**MJ CDN(`cdn.midjourney.com`)은 Cloudflare로 막혀 있다.** 컨테이너 안에서도 403이다
(5,562바이트 = CF 차단 페이지). 그대로 두면 `[6]`·`[7]`이 산출물 바이트를 받을 수 없다.

`ImageStorageType=LOCAL` + `LocalStorage.customCdn`을 설정하면 프록시가 직접 내려받아
자기 주소로 서빙한다:

```
https://cdn.midjourney.com/...        → CF 403
http://localhost:8086/attachments/... → 200  ✅
```

**이것은 선택 설정이 아니라 전제 조건이다.** 설정 전에 돌린 영상 잡은 CDN URL만 돌려줘서
받을 수 없었고, 설정 후 잡은 `localhost:8086` URL을 돌려줬다.

## G3 실측 (2026-08-12, 이미지 13잡) — `--sref`를 쓰지 않는다

**G3 통과. 단 게이트가 예상한 것과 반대 방향으로 통과했다.** 산출물은
`runs/20260812-g3-sref-probe/`에 있다(gitignore 대상). 전부 relax라 **과금 0원**이고
`officialFastRemaining`은 53040초에서 움직이지 않았다.

앵커 강도 3단계 × 같은 씬 4개로 갈랐다. 앵커는 GitHub raw 공개 URL로 넘겼다 —
`upload-discord-images`를 확인할 필요가 없었다.

| 앵커 강도 | 마감 | 씬 간 일관성 |
|---|---|---|
| `--sref` (기본 100) | **탈락.** 잉크 스크리블·수풀·프레임 선이 화면을 덮는다 | 붙긴 하나 룩이 틀렸다 |
| `--sref --sw 20` | 사실적으로 돌아오나 **사각 테두리가 뚜렷한 인쇄 도판**이 된다 | 붙는다 |
| **앵커 없음** | **채택.** 수채 워시 + 흑연 밑그림 위에 정밀·사실적 묘사 | **붙는다** |

**앵커 3장이 프롬프트를 이긴다.** ADR-0023의 `BASE_STYLE`에는
`realism dominant over painterly looseness`가 들어 있는데, `--sref`가 걸리면 그 절이 죽고
앵커의 느슨한 스케치가 이긴다. 사람이 대조군(`s27-present-control`)을 보고 그 마감을
택했고, 2차 4씬이 그 선택을 재확인했다.

**핵심은 일관성의 출처였다.** 앵커 없이도 흰 종이 바탕·수채/흑연·가장자리 소실이 4개 씬에
일관되게 나온다. 씬 간 일관성을 만들던 것은 앵커가 아니라 **프롬프트의 `BASE_STYLE`**
이었다. 앵커는 그 위에 다른 룩을 덧씌우고 있었을 뿐이다.

> `assets/style_anchors/` 3장을 지우지는 않는다. ADR-0023이 `BASE_STYLE`을 확정할 때 쓴
> 승인 기준물이고, NB2 복귀 경로(ADR-0021)가 여전히 첨부해서 쓴다.

### 단면 샷은 유지한다 — 막힌 것은 "구조물 절단면" 하나다

G3에서 `s03-section`(댐 단면)이 두 변인 모두에서 **브루탈리즘 건물**로 나왔다.
스타일 실패가 아니라 **의미 실패**였다 — 그림은 잘 그려졌고 대상이 틀렸다.

이것이 "단면 샷을 스펙에서 빼야 하나"라는 질문을 열었고, 실측 52씬으로 먼저 쟀다.
`diagram` 스케일은 **52씬 중 11씬(21%)**, 그중 좁은 의미의 단면은 **5씬(10%)**이고
후버댐 4·피사 1로 토픽에 쏠린다. 드물지만 후버댐의 `turning_point`·`solution_step`이
둘 다 단면이다 — **"그래서 발상을 뒤집습니다" 직후의 지불 지점이다.**

그래서 빼는 대신 프롬프트를 재측정했다 (`runs/20260812-section-dialect-probe/`, relax 7잡).

| 변인 | 대상 | 절단면 |
|---|---|---|
| A 대상 먼저, 절단면을 술어로 | ✅ | ❌ 멀쩡한 댐 |
| B 도면 장르 선언 | △ | △ 상부만 열림 |
| C 앞쪽 절반 제거 | ✅ | △ 윗부분만 |
| **D 지반·지층 단면 (피사)** | ✅ | **✅ 성공** |
| **Z 실패한 원본 재투입** | ❌ 건물 | ❌ — **실패 재현. seed 운이 아니었다** |
| **E 시공 중 블록 격자 (전경)** | ✅ | **불필요 — 성공** |
| **F 블록 이음부 (근경)** | ✅ | **불필요 — 성공** |

**Z가 이 표의 핵심이다.** 대조군 없이는 A~C의 개선이 어법 덕인지 재추첨 덕인지 갈리지
않는다. 같은 실패가 그대로 재현됐으므로 원인은 프롬프트다.

세 가지가 확정됐다.

1. **대상 명사를 살리면 대상은 잡힌다.** A·B·C 모두 아파트 건물이 댐으로 바뀌었다
2. **지반·지층은 잘린다(D). 구조물은 안 잘린다(A·B·C 3전 3패).** MJ의 "댐" 프라이어가
   멀쩡한 댐 사진이고 `realism dominant`가 단면에 필요한 도해적 추상을 밀어낸다.
   지질 단면도는 MJ가 아는 장르라 통과한다
3. **후버댐은 자를 필요가 없다.** 지식 카드(NPS·USBR, `[high]`)가 기둥 블록이 시공 중
   **외부에 드러나 있었다**고 적는다 — "a series of individual columns", "each block
   interlocked ... like a Lego set". E·F가 그 장면을 정확히 냈다

따라서 `section_diagram`·`cross_section`·`present_section`을 룰 테이블에서 빼지 않는다.
`[5]` MJ 방언이 대상에 따라 서술을 고르면 된다 — **지반은 절단면으로, 구조물 내부는
시공 중·미완성으로.** 이 규칙을 `specs/03-visual-rules.md`에 넣는 것은 룰 테이블 변경이라
별도 ADR로 다룬다.

### 채택 마감의 판정 기준 — 가장자리 여백은 기준이 아니다

초안에서 나는 E·F가 "가장자리가 종이로 빠지지 않아 채택 룩에서 벗어난다"고 적었다.
**사람이 그것을 기각했다 (2026-08-12).** E·F를 보고 "지금이 딱 좋다"고 판단했다.

| | 기준인가 |
|---|---|
| **종이에 스케치한 느낌** | **예** |
| **정밀하고 사실적인 묘사** | **예** |
| 가장자리가 맨 종이로 사라지는 것 | **아니다** — 안 보여도 무방하다 |

`BASE_STYLE`의 `detail and colour fall away toward the edges into bare paper`는
**문구로는 남긴다** — ADR-0023이 실호출로 검증한 그대로이고, 룩을 그쪽으로 미는 역할을
한다. 바뀌는 것은 **판정**이다. 결과물이 풀블리드로 나왔다는 이유만으로는 반려하지 않는다.

> 이 정정이 G3 판정을 흔들지는 않는다. 다만 **위 표에서 앵커 없음을 택한 근거 중
> "가장자리가 맨 종이로 사라진다"는 항목은 이제 근거가 아니다.** 남는 근거는 두 개다 —
> `--sref`(100)가 낸 잉크 스크리블을 사람이 명시적으로 기각했다는 것, 그리고 **앵커 없음이
> 같은 품질을 더 적은 기계장치로 낸다는 것**(앵커 호스팅·`--sref`·계약 공백 #2·`digest`
> 재료 변경이 전부 사라진다). `--sw 20`이 지금 기준으로 통과할 가능성은 열려 있으나,
> 통과하더라도 채택할 이유가 없다.

### 진짜 남는 값 — 하단 1/3이 안 비었다

가장자리와 **별개 문제**이고, 이쪽은 미감이 아니라 계약이다.

`COMPOSITION`은 `subject placed in the centre to upper third, bottom third left empty`인데
**E·F 모두 하단 1/3이 안 비었다** (E는 물·암반, F는 블록으로 꽉 찼다). ADR-0023은 검증
6장이 전부 하단이 비었던 것을 근거로 **"원래 여백으로 끝내는 그림이라 억지로 비우지 않아도
비워진다"**고 적었는데, 피사체가 조밀하면 그 전제가 깨진다.

이것이 자막에 직접 걸린다. ADR-0023은 흰 종이를 전제로 자막을 **`검정 글자 + 흰 외곽선`**
으로 뒤집었다. 하단이 어두운 콘크리트·물이면 검정 글자가 묻힌다.

`[8] overlay`가 후처리라 대응할 여지는 있지만(자막 뒤 반투명 판 등 — ADR-0019가 레이어 A를
없앤 것과 충돌하는지 따로 봐야 한다), **먼저 `[5]` 방언이 `bottom third left empty`를 더
강하게 밀 수 있는지 본다.** 사례가 E·F 두 장뿐이므로 첫 실제 편에서 빈도를 세는 것이 먼저다.

### 계약 공백 — 1건 해결, 1건 소멸, 1건 신규

**#1 (4장 중 선택) — 해결.** G1에서 태스크 응답의 `imageUrls`가 **4장을 직접 URL 배열로
준다**는 것을 확인했다(`0_0`~`0_3`). **`imageUrls[0]` 고정**이면 되고, 순수 인덱스 선택이라
ADR-0001을 만족한다.

초안의 "U1 고정" 안은 **철회한다.** `MJ::JOB::upsample::1::<uuid>` 버튼으로 별도 잡을
제출할 필요가 없다 — 초안이 걱정한 "편당 이미지 잡 26 → 52"는 발생하지 않는다.

> 프록시는 4장을 병합한 그리드도 로컬에 저장한다(`attachments/merges/...`,
> **1632×2912** = 816×1456의 2×2). `imageUrls`가 개별 URL을 주므로 크롭할 필요는 없지만,
> 개별 URL이 막히면 이쪽을 4분할하는 경로가 남아 있다.

**#2 (`--sref` 입력 형태) — 소멸.** 푼 것이 아니라 **풀 필요가 없어졌다.** G3에서
`--sref`를 쓰지 않기로 했으므로(위 "G3 실측") 앵커를 MJ에 넘기는 문제 자체가 사라진다.
`POST /mj/submit/upload-discord-images`의 응답 형태는 끝내 확인하지 않았고, 확인할
이유도 없다.

따라서 `ImageRequest.digest`의 재료도 **바꾸지 않는다.** MJ 경로에는 앵커가 들어가지
않으므로 앵커 파일명이 다이제스트에서 빠질 뿐, 업로드 URL 같은 새 재료가 생기지 않는다.

> G3 탐침 자체는 앵커를 **GitHub raw 공개 URL**로 넘겨 돌렸다. 업로드 대행이 필요 없는
> 우회로가 실재한다는 뜻이므로, NB2 복귀 시가 아니라 **MJ에서 앵커를 다시 쓰게 되는
> 경우가 생기면** 이 경로부터 본다.

**#3 (프롬프트 방언) — 신규.** 초안에 없던 항목이다. `prompts.json`의 `prompt`는
**Nano Banana용 여러 줄 자연어**다(`Subject:` / `Shot:` / `Style:` / `Framing:` 블록,
한국어 포함). MJ는 **한 줄 + `--ar` + `--no`** 문법이라 그대로 넣을 수 없다.

G1에서는 사람이 손으로 옮겨 붙여 검증했다. `[5] prompt`가 MJ 방언을 내야 한다:

| NB2 | MJ |
|---|---|
| `style.aspect_ratio: "9:16"` | `--ar 9:16` |
| `negative_prompt` 문장 | `--no a, b, c` |
| 여러 줄 블록 | 한 줄 콤마 나열 |
| 앵커 파일 첨부 | **없음** — MJ 경로는 앵커를 안 쓴다 (G3) |

**`style.resolution: "2K"`는 MJ에 대응 파라미터가 없다.** MJ v8.2가 9:16에서 내는 값은
**816×1456으로 고정**이고, 이는 ADR-0005의 "2K" 규정(NB2 실측 1536×2752)보다 낮다.
최종 출력 1080×1920에는 **1.32배 업스케일**이 필요하다 — 영상의 2.33배보다는 낫지만
스펙과의 충돌이므로 ADR-0005 수정 대상이다.

- ~~**G3 실패(`--sref` 룩 일관성 미달)** → 이미지는 NB2로 복귀~~ → **해소됨** (2026-08-12

  씬 간 룩이 흔들리는 것**이 새 위험이다. G3은 씬 4개로 쟀고 실제 편은 25~27씬이므로,
  **첫 실제 편에서 편 전체의 일관성을 다시 본다.** 흔들리면 이미지는 NB2로 복귀한다
  (ADR-0021 경로가 살아 있다)
- **계정 정지** → `nano_banana.py`·`kling` 경로로 즉시 복귀. **이 복귀 경로를 지우지 않는
  것이 위 "바뀌는 코드"에서 `nano_banana.py`를 유지하는 이유다**
- **`trueai-org/midjourney-proxy` 유지 중단** (novicezk가 1년째 정체된 전례) → Playwright
  + 영구 프로필 자체 구현 또는 위 복귀 경로
- **월 17편 초과** → Pro $60 승급 (Relax 영상 무제한, Stealth mode)
- Stealth mode 부재로 프롬프트·룩이 공개 갤러리에 노출되는 것이 문제가 되면 Pro 승급
- **리프레시 토큰이 만료·폐기돼 자동 갱신이 끊기면** (자동 갱신 자체는 2026-08-12에
  확정됐다 — 위 G1 실측 참조) → **`[0] token` 단계를 신설한다.** MJ는 Firebase Auth를
  쓰므로(JWT `iss` = `securetoken.google.com/authjourney`) 브라우저 없이 갱신할 수 있다:

  ```
  POST https://securetoken.googleapis.com/v1/token?key=<공개 웹 API 키>
       grant_type=refresh_token&refresh_token=<AuthUserTokenV3_r>
  →    { id_token, refresh_token, expires_in }
  ```

  새 `id_token`으로 쿠키 문자열을 다시 만들어 프록시 `userToken`에 PUT한다. **stdlib
  `urllib`만으로 되므로 `requirements.txt`가 두 줄로 유지된다** (ADR-0021과 같은 판단).
  검토했다 탈락시킨 대안: Playwright(+300MB, 의존성 정책 위반), CDP(크롬 프로필 충돌),
  **크롬 쿠키 DB 직접 복호화(Chrome 127+ App-Bound Encryption으로 불가)**
- **리프레시 토큰까지 만료/폐기되면** 사람이 브라우저에서 쿠키 문자열을 다시 넣어야 한다.
  이것은 자동화할 수 없다 — Google OAuth + 휴대폰 2FA 승인이 필요하기 때문이다
- **`cf_clearance` 무효화** → Cloudflare가 판단으로 언제든 무효화할 수 있다. 계정 정지가
  아니라 일시적 차단이며, 쿠키 재투입으로 복구된다. 프록시에 CF 자동 인증 기능이 있으나
  별도 captcha 서버 컴포넌트가 **Windows 전용 바이너리**라 위 크래시와 같은 문제일 수 있다
