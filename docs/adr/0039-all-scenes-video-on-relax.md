# ADR-0039: 전 씬을 영상으로 만든다 — 영상은 relax, 이미지는 fast로 모드를 뒤집는다

- 상태: 승인 (**부분 후속 → ADR-0043**: 인포씬은 Veo first/last로 분기한다. 나머지 씬의 전 씬 MJ 영상·모드 배치는 유지)
- 날짜: 2026-08-19
- 관련 스펙: specs/02-beat-schema.md, specs/03-visual-rules.md, specs/05-pipeline.md, specs/schema/vocab.json, specs/schema/beat-defaults.json, specs/schema/scene.schema.json, specs/schema/sceneplan.schema.json
- 관련 ADR: **ADR-0006(하이브리드 — 본 ADR이 폐기한다)**, **ADR-0025 §2(이미지 relax·영상 fast 강제 분리 — 본 ADR이 뒤집는다)**, ADR-0031(§4 동시 제출), ADR-0032(프록시 경계), ADR-0033 §3(연출은 어휘에서 고르고 비면 기본값), ADR-0035(대기 상한은 프로바이더가 안다)

## 맥락

### 1. 사람 결정 — 모든 이미지를 동영상으로 (2026-08-19)

> "**모든 이미지를 동영상으로 뽑아야 해.**"

ADR-0006이 "유체 모션이 서사상 필요한 씬에만, 편당 상한 10씬"으로 정한 것을 뒤집는 결정이다.
아래 실측은 그 결정을 **가능하게 만든 조건**이지 결정을 대신하는 것이 아니다.

### 2. ADR-0006의 탈락 사유가 소멸했다

ADR-0006이 「전 씬 Kling」을 떨어뜨린 사유는 **하나였다 — 편당 ~$15.**

| ADR-0006이 본 것 (2026-08-07) | 오늘 (2026-08-19) |
|---|---|
| 전 씬 영상 = 편당 **~$15** | 전 씬 영상 = **GPU 0, 과금 0** |
| 하이브리드 = 편당 ~$4.5 | 하이브리드도 0. **차이가 없다** |

비용이 0이 되면서 **하이브리드를 유지할 근거가 남지 않았다.**

ADR-0006의 다른 근거 하나는 남는다 — **"원본도 전 씬 모션이 아니다."** 이것은 비용이 아니라
레퍼런스 관찰이고, 사람이 그것을 알고 뒤집었다. **되돌릴 조건으로 옮긴다.**

### 3. 실측 — Pro 전환으로 relax 영상이 열렸다 (2026-08-19)

플랜을 Standard($30) → **Pro($60)** 로 올렸다. 같은 이미지·같은 프롬프트로 잰 것이다.

| | Standard·fast | **Pro·relax** |
|---|---|---|
| 제출 | `/mj-fast/mj/submit/video` | `/mj-relax/mj/submit/video` |
| 결과 | SUCCESS | **SUCCESS** |
| `mode` | `FAST` | **`RELAX`** |
| **GPU** | **2.4분** | **0** (`30.00 → 30.00`, 동기화 2회 확인) |
| 벽시계 | 55.1초 | 205.7초 |
| 클립 | `h264 464×832 24fps 5.208초` | **동일** |

**relax의 SD 제약은 우리에게 무의미하다** — fast에서도 이미 464×832였다. 잃는 것이 없다.

프록시가 알아서 `--relax`를 붙인다. **계정의 `isRelaxVideo`는 `False`인 채로 됐다** —
토글을 건드릴 필요가 없다.

```
finalPrompt: <https://s.mj.run/…> … --motion low --bs 1 --relax  --video 1 --aspect 143:256
```

### 4. Standard에서 왜 안 됐는지도 확정됐다

ADR-0025의 정정 3번이 **"`/mj-relax/`로 던져도 `mode=FAST`로 돈다"**를 원인 없이 적어 뒀다.
원인은 프록시가 아니라 **플랜**이었고, MJ가 직접 말했다 (거절이라 과금 0):

```
Invalid request, Relax mode for video is limited to Pro and Mega plans.
Upgrade your plan or switch to Fast mode.
```

**같은 자리에서 프록시의 relax→fast 자동 변환이 못 믿을 것임도 드러났다.** 같은 날 오전에는
`/mj-relax/`로 던진 영상이 조용히 fast로 바뀌어 성공했고, 오후에는 그냥 거절됐다.
**엔드포인트를 명시해야 한다.**

### 5. 실측 — `batchSize 1`이 GPU를 3.25분의 1로 줄인다

MJ는 영상 잡 하나에 **4개**를 낸다. 우리는 U1 하나만 쓰고 셋을 버려 왔다 — 이미지에서
사분면 셋을 버리던 것과 같은 구조다 (ADR-0031 §2가 고친 그것).

| | U 버튼 | GPU |
|---|---|---|
| 기본 (4개 묶음) | 4개 | **7.8분** |
| **`batchSize: 1`** | **1개** | **2.4분** (`14.42 → 14.38`) |

`SubmitVideoDTO`에 이미 있는 필드다. 프롬프트에 `--bs 1`로 찍힌다.
**relax에서도 그대로 먹는다** — relax는 GPU가 0이라 비용 이득은 없지만, fast로 되돌아갈
경우(밴·플랜 변경)에 대비해 켜 둔다.

### 6. 실측 — 이미지는 fast가 26배 빠르고 사실상 공짜다

영상이 relax로 빠지면서 **Pro의 fast 30시간이 통째로 남는다.** 이미지에 쓴다.

| | relax | **fast** |
|---|---|---|
| 1잡 벽시계 | 180.4초 | **7.0초** |
| GPU | 0 | **0.6~0.8분** |
| 28씬 편당 (동시 3) | ~28분 | **~1.5분** |
| Pro 30시간 기준 | 무제한 | **월 80편** |

편당 GPU 22분이면 월 80편이다. **편수는 병목이 아니다.**

### 7. 편당 벽시계 — 전 씬 영상이 실제로 돈다

28씬, 동시 3 기준이다.

```
[6]  IMAGINE   fast    28/3 ×   7초 ≈  1.5분
[7]  UPSCALE   relax   28/3 ×  10초 ≈  1.6분
     VIDEO     relax   28/3 × 206초 ≈ 32분
     U1 추출           28/3 ×  10초 ≈  1.6분
                                    ─────────
                                      약 36분/편 · GPU 22분
```

밤에 돌리는 파이프라인이면 문제가 없고, **월 편수 상한이 사라진다.**

### 8. 실측 — 잡이 조용히 유실되는 경로가 둘이다

둘 다 오늘 실물로 겪었다. **어느 쪽도 실패로 기록되지 않는다 — `SUBMITTED 0%`로 영구히 선다.**

| # | 언제 | 무슨 일 |
|---|---|---|
| **콜드스타트** | Docker 기동 직후, 계정 인스턴스 초기화 **전** 제출 | 프록시가 접수하지만 디스코드로 나가지 못한다. 초기화 완료 2분 46초 전에 던진 잡이 15분 타임아웃까지 죽어 있었다 |
| **모드 전환 직후** | relax → fast 전환 바로 다음 첫 잡 | MJ에서 **실행은 됐고 GPU도 빠졌는데**, 추적하던 디스코드 메시지가 `MESSAGE_DELETE`되며 프록시가 결과를 놓쳤다. fast 3잡 중 1잡 |

전환 없이 연속으로 던진 2잡은 7초에 정상이었다. **모드를 섞는 설계가 이 위험을 만든다** —
이 ADR이 이미지 fast·영상 relax로 나누기 때문에 계정 모드가 편마다 오간다.

## 결정

### 1. 전 씬을 영상으로 만든다 — ADR-0006 하이브리드 폐기

- **`motion`의 기본값이 `mj_video`다.** `specs/schema/beat-defaults.json`의 `fallback`에
  넣는다. 씬이 값을 비우면 영상이 된다 (ADR-0033 §3의 구조 그대로)
- **`[1s] sceneplan`은 `motion`을 고르지 않는다.** 전 씬 영상이므로 고를 것이 없다.
  프롬프트에서 뺀다
- **씬 계약에서 `motion`을 required → 선택으로 내린다** (`scene.schema.json`,
  `sceneplan.schema.json`). 비면 기본값이 정한다
- **편당 영상 씬 상한을 폐기한다.** `vocab.json`의 `mj_video.max_scenes`를 지운다.
  GPU가 0이라 셀 이유가 없다

**`motion` 필드와 `kling`은 남긴다.** ADR-0025가 "MJ가 밴당하면 돌아갈 곳"으로 남긴
차선이고, 그 경로는 편당 과금이 되살아나므로 **`kling`의 `max_scenes`는 그대로 둔다.**
`kenburns`는 이제 **선택지가 아니라 강등 결과**다.

### 2. 모드 배치를 뒤집는다 — 이미지 fast, 영상 relax (ADR-0025 §2 대체)

| 단계 | 엔드포인트 | 근거 |
|---|---|---|
| `[6] imagegen` | **`/mj-fast/mj/submit/imagine`** | 7초 vs 180초. GPU 0.6~0.8분은 월 80편 여유 |
| `[7]`의 UPSCALE | `/mj-relax/mj/submit/action` | GPU 0. 급하지 않다 |
| `[7]`의 VIDEO | **`/mj-relax/mj/submit/video`** | **GPU 0.** 전 씬 영상을 가능하게 하는 유일한 차선 |

**엔드포인트를 프록시의 자동 변환에 맡기지 않는다** (§4). 단계가 명시한다.

### 3. `[7]`은 `batchSize: 1`을 보낸다

4개를 사서 1개를 쓰지 않는다. relax에서 비용 이득은 없지만 **fast로 되돌아갈 때 3.25배가
걸려 있고**, 큐에 얹는 부하도 준다.

### 4. `[6]`·`[7]`은 시작 전에 계정 인스턴스가 붙었는지 대조한다

ADR-0032가 "프록시 실제 상태와 어긋나면 호출 없이 멈춘다"로 정한 대조 항목에
**"계정이 실제로 작업을 받을 수 있는 상태인가"가 없었다.** 추가한다 — 27씬을 콜드스타트에
던지면 전부 조용히 큐에서 썩는다.

**모드 전환 유실은 막지 않고 흡수한다.** `[6]`에는 이미 씬당 1회 재시도 + 인접 씬 폴백이
있고, 파이프라인 순서가 `[6] 전 씬 → [7] 전 씬`이라 편당 전환이 1~2회뿐이다.
다만 **`SUBMITTED`에서 진행이 멈춘 잡을 감지할 수단이 없다** — ADR-0035로 대기 상한을
프로바이더에 맡겼으므로 그런 잡은 어댑터 기본값(1800초)을 꽉 기다린다. 아래 되돌릴 조건 3번.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| **하이브리드 유지** (ADR-0006 그대로) | 손댈 것이 없다. 원본 채널도 전 씬 모션이 아니다 | 사람 결정과 어긋난다 | **결정 사항이다.** 그리고 유지할 **비용 근거가 사라졌다** (§2) — 하이브리드와 전 씬 영상의 과금이 똑같이 0이다 |
| **전 씬 영상 + fast 유지** | 편당 36분 → 12분 | GPU 28씬 × 2.4분 = 67분/편 → **월 27편** | 편수에 상한이 다시 생긴다. 그 상한을 없애려고 Pro로 올린 것이다. 급한 편만 예외로 fast를 쓰는 것은 `--jobs`처럼 사람 인자로 열어 두면 된다 |
| **`motion` 필드를 없앤다** | 전 씬 영상이면 씬마다 고를 것이 없다. `mj_video` 조용한 강등 버그가 구조적으로 사라진다 | 두 스키마·`vocab`·`carried_fields`·`timed_scenes`·`[1s]` 프롬프트·테스트가 함께 움직인다. **`kling` 폴백 차선이 사라진다** | ADR-0025가 밴 대비로 남긴 차선을 없애는 값이 아니다. 기본값을 뒤집는 것으로 같은 결과를 얻는다 |
| **HD 영상(720p)으로 간다** | 화소 4배. 1080 업스케일 배율 2.33 → 1.5배 | **HD는 fast 전용**이고 6분/클립 → 28씬이면 168분/편 → 월 10편 | 전 씬 영상과 양립하지 않는다. **480p 룩 문제(ADR-0025 G2)는 이 ADR이 풀지 않는다** — 첫 실제 편에서 다시 본다 |

| `specs/schema/scene.schema.json`·`sceneplan.schema.json` | `motion`을 `required`에서 제거 |

| 비용 기준선 | 편당 GPU 22분 (이미지). 영상 0 |

### 이 결정이 같이 닫는 것

**`mj_video` 조용한 강등** (worklog 2026-08-19 (13) 0번, ADR-0025 §3 정정). `[7]`에
분기가 없어 `mj_video`가 경고도 `demoted_from`도 없이 Ken Burns로 렌더되던 문제가,
분기를 만들면서 사라진다.

### 옛 대본은 다시 돌린다 — 마이그레이션하지 않는다 (ADR-0036)

후버댐 대본은 `motion`이 `kenburns` 26 / `mj_video` 2다. `[7]`은 값이 있으면 그대로 쓰므로
이 대본은 전 씬 영상이 되지 않는다. **`[1s]`부터 다시 돌린다.** 백필하지 않는다.

### 되돌릴 조건

1. **원본 채널의 관찰이 옳았던 것으로 드러나면** — ADR-0006이 "원본도 전 씬 모션이 아니다"로
   적어 둔 그것이다. 전 씬 영상이 산만하거나 리텐션이 떨어지면 하이브리드로 돌아간다.
   **판단 근거는 완성된 편을 사람이 보는 것이고, 비용은 이제 근거가 아니다**
2. **relax 큐가 편당 36분을 크게 넘기면.** 오늘 영상 1잡이 206초였는데 relax 대기는 남의
   부하가 정한다 (ADR-0035에서 5배 편차를 실측했다). 편당 몇 시간이 되면 fast 예외 인자를
   기본으로 올리거나 편당 영상 씬 수를 다시 제한한다
3. **`SUBMITTED`에서 멈춘 잡이 반복되면.** 오늘 fast 3잡 중 1잡이 그랬다. 그 빈도가 유지되면
   ADR-0035의 "대기 상한을 선언하지 않는다"를 **진행 없음 감지**로 보완해야 한다 —
   상한이 아니라 "N초 동안 `progress`가 안 움직이면 죽은 잡으로 본다"는 다른 종류의 판정이다
4. **플랜을 Pro 아래로 내리면** relax 영상이 즉시 막힌다 (§4). 그때는 전 씬 영상이 불가능하다
