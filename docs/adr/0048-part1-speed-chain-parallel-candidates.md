# ADR-0048: 1부 속도 개편 — draft 체인을 [1b]·[2]까지 잇고, [1w]는 병렬 후보 K개를 쓰고, 리서치 타임아웃을 실측 위로 올린다

- 상태: **승인** (2026-08-21, 사람 결정 — "승인할테니 바꾸고 실제 새로운 소재를 돌려서
  실측해봐. 테스트를 너무 작게 하지 말고 3개 이상의 소재를 돌리고." 실측 검증이 조건이다)
- 날짜: 2026-08-21
- 관련 스펙: specs/05-pipeline.md
- 관련 ADR: ADR-0029(옛 [1]을 [1a]·[1s]·[1w]로 가름 — draft 체인의 전제),
  ADR-0044(재생성 루프 없음 — 체인의 실패 처리 규칙이 여기서 온다),
  ADR-0047(전달 축 — 후보 변주의 축이 "전달"인 근거), ADR-0008(헤드리스 구독 — 동시
  세션의 한도 제약), ADR-0009(세션 독립 — 병렬 후보가 지켜야 하는 격리)

## 맥락

### 실측 — 1시간짜리 "대본 생산"에서 대본은 19분이다

호르무즈 편 1부 전체(2026-08-20, `runs/20260820-horeumujeu-*/logs/*.json`의
`duration_api_ms`와 파일 mtime):

| 구간 | 실측 | 성격 |
|---|---|---|
| [0b] 01-research | 797.6초 | 웹 세션 |
| [0b] 02-verify | 797.9초 **+ 실패 attempt1 ≈15분** | 타임아웃 → 통째 재실행 |
| [0b] 03-critique + 04-factsheet | 526.6초 | |
| [1a] outline | 121.4초 | |
| [1s] sceneplan | 291.8초 | |
| [1w] write | 679.4초 | 1부 최장 LLM 단계 |
| [1b] score | 24.1초 | **후보 1개 — 사실상 통과의례** |
| 수동 명령 사이 공백 | **≈53분** | factsheet→draft 25분, draft→score 28분 |

- 대본 3단계+채점의 LLM 시간은 **18.6분**이다. 체감 1~2시간의 나머지는
  ① 명령이 끊기는 지점의 사람 대기(≈53분), ② [0b] 블록(성공분 35.4분), ③ 재시도
  낭비다.
- 재시도 낭비의 실측: 호르무즈 02-verify는 attempt2에서야 성공(공백 28.7분 중 성공분은
  13.3분), 이란 01-research는 **attempt5**다. 성공 세션의 실소요가 762~930초인데
  서브스텝 타임아웃이 900초라 **경계 위에 있다** — 900초 직전에 끝날 세션이 죽고
  처음부터 다시 돈다. 타임아웃 재시도는 부분 재개가 아니라 전체 재실행이다.
- `draft`([1a]+[1s]+[1w])는 이미 공백 없이 18분에 돌았다 (13:45→14:03). 공백은
  체인이 끊기는 곳(factsheet→draft, write→score)에서만 생겼다.

### 문제 셋 (사람 지적, 2026-08-21)

1. 대본 1편에 1시간+ → 테스트 반복이 그만큼 느리다.
2. 퀄리티 체크를 어느 지점에서 해야 하는지 모호하다.
3. 대본이 마음에 안 들었을 때 재생성 비용(시간)이 크다.

## 결정

넷을 함께 바꾼다. 새 단계는 없다 — 오케스트레이션·동시성·상수만 바뀐다.

1. **`draft` 체인을 [1b] score → [2] validate까지 확장한다.** 순서는 스펙 05의 단계
   순서 그대로다. 각 단계의 실패 처리 규칙(ADR-0044: 중단·보고, 재생성 없음)은 그대로고,
   단계는 여전히 파일로만 통신한다. `package`([0a]+[0b]) 전례와 같은 성격의 배선이다.
2. **[1w]는 후보 K개(기본 3)를 동시 세션으로 쓴다.** `05-candidates/01.json..0K.json`.
   후보의 변주 축은 **전달**(문장·문체·훅 문장의 최종 형태, ADR-0047)이다 — K세션 모두
   같은 `08-sceneplan.json` 위에서 쓰고, 씬 구조·요지는 계획에서만 온다 (ADR-0029 불변).
   세션끼리는 완전히 독립이다(프롬프트 동일, 컨텍스트 공유 없음 — ADR-0009). 씬 단위
   재청(ADR-0044)은 후보마다 자기 세션에서 그대로 돈다. 벽시계 시간은 후보 1개일 때와
   같고(병렬), 채점이 실질이 되며, 마음에 안 들면 재생성 대신 **이미 있는 차선 후보**를
   고른다.
3. **[1b]는 검증 통과 후보만 채점한다.** [1w]가 후보별 검증 결과를 남기므로, [1b]는
   `validate_candidate`를 통과한 후보만 세션에 올린다. 전 후보가 검증 실패면 [1w]가
   실패로 멈춘다 (ADR-0044). 최종 게이트 [2]는 그대로다 — 선발된 06-script.json을
   마지막에 한 번 더 본다.
4. **[0b] 01-research·02-verify의 세션 타임아웃을 900→1500초로 올린다.** 성공 실측
   762~930초 위에 ~60% 마진. 03·04(실측 245~443초)는 900초를 유지한다. 아울러
   **타임아웃으로 인한 재시도는 2회로 제한한다**(한도/과부하 재시도 5회와 분리) —
   타임아웃 재시도는 회당 타임아웃만큼 태우는 전체 재실행이라, 5회면 최악 2시간을
   조용히 태운다.

운영 결정 하나: **[0b]는 대본 반복과 분리해 미리 돌려 둔다.** 팩트시트는 소재당 한 번인
캐시 가능한 입력이다(한계비용 0, specs/00). 프롬프트·단계 수정의 테스트 루프는 기존
팩트시트 재사용으로 ~19분이 된다. 별도 코드 없이 `package`를 앞서 돌리는 운영 지침이다.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| 훅별 후보 (outline의 `hook_candidates`마다 [1s]+[1w] 한 벌) | 후보 다양성이 구조 수준 | `08-sceneplan.json`이 복수가 되고 [1a]의 `chosen_hook` 계약이 바뀐다. K×[1s] 세션 추가 | 계약 변경 폭이 크다. 전달 변주 후보의 점수가 서로 붙어 나오면(변별력 부족) 그때 재검토 |
| 단계별 모델 다이어트 (sceneplan·factsheet를 Sonnet으로) | 해당 단계 ~2배 단축 추정 | 품질 저하 여부 미실측 | 품질 실측 프로브가 선행돼야 한다. 별도 결정으로 미룬다 |
| 타임아웃 유지 + 재시도 횟수만 축소 | 코드 변경 최소 | 경계 위 타임아웃(900 vs 실측 930)이 그대로라 성공 직전 세션을 계속 죽인다 | 낭비의 원인이 재시도 횟수가 아니라 경계값이다 |
| [1w] 후보를 순차로 K개 | 동시 세션 한도 걱정 없음 | 벽시계 K×11분 — 속도 문제를 되려 키운다 | 목적(속도)과 정면 충돌 |

## 결과

- 코드: `cli.py`(draft 체인 확장), `stages/write.py`(병렬 후보 K), `stages/score.py`
  (통과 후보만 채점), `stages/research.py`(서브스텝 타임아웃), `llm/claude_code.py`
  (타임아웃 재시도 상한 분리)
- 스펙: specs/05-pipeline.md의 [1w]·[1b] 줄에 후보 K·채점 대상 명시
- 예상 효과: 대본 반복 루프(팩트시트 재사용 시) 1시간+ → **~19분 무개입**, 재생성
  리스크는 후보 선택으로 흡수. 콜드 스타트(리서치 포함)는 타임아웃 정비로 재시도 낭비
  ~15분×N 제거
- 동시 세션은 구독 한도를 나눠 쓴다 (ADR-0008). K=3 병렬이 한도 재시도를 유발하면
  백오프가 받지만, **한도 도달이 반복 관측되면 K를 낮추는 쪽이 먼저다**
- 되돌릴 조건: ① [1b] 점수가 후보 간 변별력이 없으면(3회 연속 총점 차 ≤ 1) 전달 변주
  후보는 비용만 쓰는 것이다 — K를 줄이거나 훅별 후보로 재검토. ② 동시 세션이 한도를
  상시 치면 순차+빠른 모델 조합을 재검토
- 미결로 남긴 것: [2b] judge를 outline 직후로 두는 품질 체크 지점 결정 — 새 단계
  추가라 별도 ADR로 다룬다
