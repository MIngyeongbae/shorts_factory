# ADR-0030: `[4] refpack` — 씬별 실사 참조를 모으고, 첨부와 서술 두 경로로 쓴다

- 상태: 제안
- 날짜: 2026-08-13
- 관련 스펙: specs/03-visual-rules.md, specs/05-pipeline.md, specs/06-topic-research.md
- 관련 ADR: ADR-0017(1부↔2부 경계), ADR-0020(2부 계약), ADR-0025(MJ 프록시), ADR-0027(방언), ADR-0028(subject_anchor)

## 맥락

ADR-0028이 텍스트로 대상을 고정하는 데까지 갔다. **그런데도 텍스트 지시에는 상한이 있다.**

| 시도 | 결과 |
|---|---|
| `협곡을 가득 메운 거대한 덩어리, 콘크리트` (정체 없음) | 협곡과 강만 (ADR-0028) |
| `협곡을 가득 메운 거대한 콘크리트 댐 덩어리, 후버댐` | 4/4 성공 — 다만 **실제 후버댐인지는 모델의 기억에 달렸다** |
| 1930년대 냉각 강관 배치, 블록 축조 순서 같은 **공정 장면** | 검증 수단이 없다 |

고유명사가 통한 것은 모델이 후버댐을 이미 알기 때문이다. **이 채널의 소재는 대부분
그렇지 않다** — 국가 무관 건축·토목·문화기술사(ADR-0016)이고, 판별 기준이 "문제 해결
서사"라서 오히려 덜 알려진 구조물이 자주 온다. 이름을 적어도 모델이 모르면 흔한 사물로
채운다.

**사람은 이 문제를 사진을 찾아 해결한다.** 지금 파이프라인에는 그 단계가 없다.

`[0b] research`가 팩트시트를 만들 때 웹을 이미 뒤진다(스펙 06). 그런데 **글의 근거만
모으고 그림의 근거는 안 모은다.** 같은 검색에서 나오는 사진을 버리고 있다.

## 결정

**`[4] refpack`을 신설한다.** 씬별로 실사 참조 사진을 모아 `runs/{run_id}/refs/`에
저장하고 `refs.json`으로 계약한다.

### 자리는 2부의 빈 번호 `[4]`다

```
06-script.json (읽기 전용, ADR-0017)
  ├ [3] tts+sync
  ├ [4] refpack     ← 신설
  └ [5] prompt
        셋 다 06-script.json만 읽는다 — 선후가 없다
  → [6] imagegen  (prompts.json + refs.json)
```

`[4]`는 스펙 05의 단계 목록에서 실제로 비어 있던 번호다. 재배열이 필요 없다.

**1부에 두지 않는 이유:** 1부↔2부 경계는 `06-script.json`과 `judgment/human.json`
**둘뿐**이라는 것이 ADR-0017이다. 참조 사진을 1부에 두면 경계 파일이 늘고 그 ADR을
깬다. 그리고 참조는 **go 승인분에만** 필요하다 — 반려될 대본의 사진을 미리 받을 이유가 없다.

### 계약: `refs.json`

```json
{
  "run_id": "20260813-hoover-dam",
  "scenes": [
    {"scene_id": 6,
     "query": ["Hoover Dam column blocks construction 1934", "후버댐 블록 타설"],
     "description": "협곡을 가로질러 계단형으로 쌓인 직육면체 블록들. 블록마다 높이가 달라 톱니처럼 어긋난다. 회백색 거친 콘크리트 표면",
     "images": [
       {"file": "refs/s06/01.jpg", "source_url": "https://...", "license": "public-domain",
        "credit": "US Bureau of Reclamation", "attachable": true,
        "shows": "블록 축조 중인 댐 전경"}
     ]},
    {"scene_id": 22, "query": [], "description": "", "images": []}
  ]
}
```

- **`description`이 첫째 산출물이다.** 사진에서 눈으로 읽어 낸 것을 한국어로 적는다.
  재질·색·형태·배치 — `subject_anchor`가 명사 몇 개로 하던 일을 구절로 한다
- `images`는 둘째 산출물이다. `attachable`이 첨부 가능 여부다
- **비어도 된다.** 도해 씬(`subject_scale: diagram`)이나 실물이 존재하지 않는 개념 씬에는
  참조가 없다. 부재를 경고하지 않는다 — ADR-0028의 선택 필드와 같은 태도다

### 소비는 두 경로다. 한쪽이 죽어도 다른 쪽이 돈다

| 경로 | 소비자 | 무엇을 |
|---|---|---|
| **서술** | `[5] prompt` | `description`을 프롬프트에 싣는다 |
| **첨부** | `[6] imagegen` | `attachable: true`인 파일을 MJ 이미지 프롬프트로 붙인다 |

**강등 사다리: `첨부+서술 → 서술 → 없음`.** 첨부가 막히는 경우가 셋이다 — 프록시에
업로드 경로가 없거나, 라이선스가 불명이거나, 첨부가 스타일을 이길 때(아래 G2). 어느
경우든 서술 경로는 그대로 산다. **두 경로를 한 몸으로 만들지 않는 이유가 이것이다.**

### 라이선스는 기록하고, 불명이면 첨부하지 않는다

- `license`·`source_url`·`credit`을 `refs.json`에 남긴다. 사후에 어느 사진이 어느 씬에
  들어갔는지 되짚을 수 있어야 한다
- **`public-domain`·`cc0`·`cc-by` 계열만 `attachable: true`다.** 불명·저작권 있음은
  `false`이고 **서술 경로만** 탄다. 사람이 사진을 보고 말로 옮기는 것은 스타일 모방이
  아니라 사실 확인이다
- 최종 산출물에 참조 사진 자체가 들어가는 일은 없다. 이미지 프롬프트는 **입력**이다

### `description`은 `subject`를 대체하지 않는다

`subject`·`subject_anchor`는 `06-script.json`에 있고 그것이 무엇을 그릴지 정한다.
`description`은 **그것이 실제로 어떻게 생겼는지**를 더한다. 값의 출처는 여전히 하나다
(ADR-0020) — 겹치면 `subject`가 이긴다.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| **`[0b] research`가 팩트시트에 사진도 담는다** | 단계가 안 는다, 검색 1회 | 씬이 아직 없다 | 참조는 **씬 단위**로 필요하다. 팩트시트 시점에는 어떤 장면을 그릴지 정해지지 않았다. 그리고 반려될 대본의 사진까지 받는다 |
| **`[5] prompt`가 검색까지 한다** | 파일 하나 안 는다 | `[5]`는 순수 룰 변환이다 | ADR-0001. 웹에서 무엇을 고를지는 판단이고 `[5]`에 판단을 넣으면 룰 테이블의 의미가 없어진다. `[5]`가 LLM 세션이 되면 방언 변환의 결정성도 잃는다 |
| **서술만 뽑고 사진은 안 쓴다** | 저작권 노출 0, 프록시 무관 | 이름을 모르는 구조물에서 여전히 약하다 | 서술도 결국 텍스트다. ADR-0028이 부딪힌 상한을 다시 만난다. 다만 **강등 사다리의 한 칸으로 남긴다** |
| **사진 첨부만 하고 서술은 안 쓴다** | 단계가 단순하다 | 첨부가 막히면 아무것도 안 남는다 | 프록시 업로드 지원이 미확인이고(G1), `--sref`가 `BASE_STYLE`을 이긴 전례가 있다(ADR-0025 G3). 한 다리로 서지 않는다 |
| **`assets/style_anchors/`처럼 누적 자산으로** | 재사용 | 소재마다 구조물이 다르다 | 스타일 앵커는 룩이라 편을 넘어 재사용되지만 **참조는 대상이라 편에 종속**된다. `runs/`가 맞다 (ADR-0026이 지식 카드를 토픽 폴더에 둔 것과 같은 축) |

## 구현 중 확인 사항

| # | 확인할 것 | 상태 | 실패 시 |
|---|---|---|---|
| **G1** | mjopen 프록시에 로컬 이미지를 Discord CDN URL로 올리는 경로가 있는가 | **미확인** (프록시가 꺼져 있어 `/v3/api-docs` 조회 실패) | 첨부 경로를 버리고 서술 경로만 쓴다. 이 ADR의 나머지는 그대로 유효하다 |
| **G2** | 이미지 프롬프트를 붙여도 `BASE_STYLE`(펜선·수채 위 극사실)이 살아남는가 | **미확인** | `--iw`를 낮춘다(0.5 → 0.25). 그래도 스타일이 밀리면 첨부를 버린다. **`--sref`가 정확히 이렇게 실패했다** (ADR-0025 G3) |
| **G3** | 웹검색 세션이 씬에 쓸 만한 사진을 실제로 찾는가 | **미확인** | 못 찾는 씬이 많으면 `[4]`는 `description`만 내는 단계가 된다 |
| **G4** | 참조를 붙인 씬이 안 붙인 씬보다 실제로 낫는가 | **미확인** | 이 ADR을 되돌린다 |

**G2가 이 결정의 급소다.** ADR-0025 G3에서 `--sref`(스타일 참조)가 `BASE_STYLE`을 이겨
마감이 망가졌다. 이미지 프롬프트는 스타일 참조가 아니라 내용 참조라 축이 다르지만,
**같은 어텐션을 놓고 다툰다는 점은 같다.** relax는 과금 0원이므로 한 씬으로 먼저 잰다.

## 결과

**바뀌는 것**

| 파일 | 변경 |
|---|---|
| `specs/05-pipeline.md` | 단계 목록·계약 표에 `[4]`와 `refs.json` |
| `specs/03-visual-rules.md` | `description`이 프롬프트 어디에 실리는지 |
| `stages/refpack.py` | 신설. 웹검색 헤드리스 세션 + 다운로드 |
| `stages/prompt.py` | `refs.json`을 읽어 `description`을 싣는다 |
| `stages/imagegen.py` | `attachable` 파일을 첨부 (G1 통과 시) |
| `schemas/refs.py` | 신설 |

`[4]`는 헤드리스 세션에 **웹검색 도구를 준다.** 지금까지 세션에 읽기 도구만 준 것과
다르다 (ADR-0011). 파일을 쓰는 것은 여전히 오케스트레이터다 — 세션은 URL과 서술을
JSON으로 돌려주고, 내려받기는 Python이 한다.

**비용**: 검색 세션 1회(구독, 한계비용 0) + 사진 내려받기(무료). `[6]` 호출 수는
그대로다 — 참조는 프롬프트를 바꿀 뿐 잡 수를 늘리지 않는다.

## 되돌릴 조건

- **G4가 답이다.** 참조를 붙인 씬과 안 붙인 씬의 재작업률(`[6r]`, ADR-0031)에 차이가
  없으면 이 단계는 벽시계 시간만 쓴 것이다
- 사진을 찾느라 `[4]`가 편당 수 분씩 쓰는데 `description`이 `subject`를 바꿔 쓴 수준이면
  — `visual_goal`이 `text`를 바꿔 쓰면 죽은 필드라는 ADR-0022의 판정과 같은 기준이다
- 참조가 오히려 씬 간 룩을 갈라 놓으면(사진마다 시대·화질이 달라서) 첨부를 끄고 서술만 쓴다
