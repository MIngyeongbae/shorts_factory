# ADR-0061: SPA 시드 기사는 헤드리스 브라우저로 렌더해서 읽는다 — `[0f] seedfetch` 신설

- 상태: 승인
- 날짜: 2026-08-24
- 관련 스펙: specs/05-pipeline.md, specs/06-topic-research.md

## 맥락

**규칙은 있는데 실행된 적이 없다.**

specs/06 시드 기준 4(사람 결정, 2026-08-23)는 "한국 소재는 나무위키를 먼저 본다"이고,
백로그·`topics/seokbinggo/seed.md`의 시드 URL도 `https://namu.wiki/w/석빙고`다.
그런데 `[1. draft]`가 그 본문을 읽은 적이 없다.

실측 (2026-08-24):

| 대상 | 방식 | 결과 |
|---|---|---|
| `namu.wiki/w/석빙고` | WebFetch | 하단 내비게이션(보물 1~200 목록)만. 본문 유무를 직접 물으면 **"본문 없음"** |
| `namu.wiki/raw/석빙고` | WebFetch | `Loading...` 한 줄 |
| `namu.wiki/w/석빙고` | `chrome --headless=new --dump-dom` | DOM 1.23MB → 텍스트 46,874자, 그중 **본문 4,854자**(개요·역사·구조·여담·외부 링크) |
| `namu.wiki/w/쿠치사케온나` | 같음 | 텍스트 36,272자, 본문 정상. 61.5초 |
| `ja.wikipedia.org/wiki/五重塔` | 같음 | 텍스트 11,636자, 본문 정상. 2.4초 |

원인은 나무위키가 클라이언트 렌더 SPA(the seed engine)라는 것이다. WebFetch는 서버가 준
HTML만 마크다운으로 변환하므로, 서버 렌더되는 카테고리·내비게이션 템플릿만 잡히고
본문은 브라우저가 그린 뒤에야 존재한다.

**그래서 석빙고 편의 대본은 나무위키에서 오지 않았다.**
`runs/20260823-seokbinggo/logs/1-draft.attempt1.json`에 WebFetch 성공 흔적이 없고
WebSearch 1회만 있다 — `prompts/01-draft.md`의 "열리지 않으면 WebSearch" 폴백으로 빠진 것이다.
결과적으로 `topics/seokbinggo/script.md` 주장 목록의 근거 URL은 전부 국가유산청·
정책브리핑·우리역사넷이고, 시드에서 온 문장은 사실상 없다. 시드를 둔 이유(흥미·구성의
원천을 사람이 쓴 두터운 글에서 가져온다)가 그 편에서는 성립하지 않았다.

**SPA는 나무위키만의 문제가 아니다** (사람 판단, 2026-08-24). 시드 후보를 "브라우저 없이는
못 읽는다"는 이유로 버리기 시작하면 버리는 쪽이 계속 는다.

비용 근거: **새 런타임 의존성이 필요 없다.** Chrome(`C:\Program Files\Google\Chrome\...`)과
Edge(`C:\Program Files (x86)\Microsoft\Edge\...`)가 이미 설치돼 있고 `--headless=new --dump-dom`은
브라우저 CLI 기능이다. 서브프로세스 호출 하나, 변동비 0, 토픽당 1회.

## 결정

**`[0f] seedfetch`를 신설한다.** 기계 단계, LLM 0회.

설치된 Chrome(없으면 Edge)을 `--headless=new --disable-gpu --dump-dom --virtual-time-budget`으로
호출해 시드 URL을 렌더하고, `<script>/<style>`을 버리고 태그를 벗긴 텍스트를
`topics/{slug}/seed-body.md`에 저장한다. 헤더에 URL·수집 시각·글자 수를 적는다.

**본문 추출은 하지 않는다.** 사이트별 셀렉터를 파지 않고 내비게이션째로 넘기며, 본문을
고르는 일은 `[1]`이 한다 — `[1]`은 어차피 글을 읽고 흥미 대목을 고르는 세션이고,
셀렉터는 사이트마다 깨진다.

`[1. draft]`는 `seed-body.md`가 **있으면** 그것을 1차 입력으로 읽고, 없거나 그 안에서
본문을 못 찾으면 지금의 WebFetch → WebSearch 사다리를 그대로 탄다 (D-3 선택적 입력의
부재는 경고가 아니다, D-5 실패는 단계 안에서 끝난다).

`seed-body.md`는 **사람이 직접 써도 되는 파일이다** — 헤드리스가 막히는 사이트는 사람이
본문을 붙여넣으면 같은 경로로 흘러간다.

부하: 토픽당 요청 1회로, 사람이 브라우저로 문서 하나를 여는 것과 같다.

## 검토한 대안

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| **1. 사람이 본문을 붙여넣는다** | 의존성 0, 어떤 사이트든 뚫린다 | 토픽마다 수작업 1회 | SPA가 상시 조건인데 상시 수작업을 붙인다. **탈락시키지 않고 폴백으로 남긴다** — `seed-body.md`를 사람이 쓰면 동일 경로 |
| **2. Playwright / Selenium** | 대기 조건·셀렉터 제어, API가 깔끔 | 새 파이썬 의존성 + Chromium 재다운로드 ~150MB | `--dump-dom` 한 줄로 되는 일에 런타임을 더 들인다. 대기 제어가 실제로 필요해지면 그때 승격 |
| **3. `claude-in-chrome` 스킬** | 사용자 로그인·사이트 권한을 그대로 쓴다 | 대화형 확장 연결이 전제 | `[1]`이 `claude -p --allowedTools WebSearch,WebFetch` 헤드리스 서브프로세스라 붙지 않는다. 파이프라인 단계가 될 수 없다 |
| **4. 규칙을 철회한다 (나무위키를 시드에서 뺀다)** | 코드 변경 0 | SPA 시드를 영구히 버린다 | specs/06 기준 4(사람 결정)와 정면 충돌. 얇은 위키백과로 되돌아가는 것이 석빙고 편의 실패 원인이었다 |
| **5. 본문 추출기(readability·trafilatura)** | 노이즈 90%를 걷어낸다 | 새 의존성 + 사이트별 오작동 | 석빙고 문서 기준 46,874자를 통째로 읽어도 `[1]`은 구독 고정비 안이다 — 지금은 값을 못 버는 최적화. 되돌릴 조건 2에 걸리면 그때 |

## 결과

**새로 생기는 것**

- `src/shorts_factory/stages/seedfetch.py` — 기계 단계, LLM 0회
- `topics/{slug}/seed-body.md` — 렌더 텍스트 (사람이 직접 써도 되는 파일)
- cli `seedfetch` 서브커맨드

**스펙 수정 (승인 시 함께)**

`specs/05-pipeline.md` 단계 목록:

```diff
   → [0. seed]      → topics/{slug}/ 폴더 + runs/{run_id}/ 생성 (기계 단계, LLM 0회.
                        반려하지 않는다 — 매체 적합성 판정은 [1. draft] 소관)
+  → [0f. seedfetch] → topics/{slug}/seed-body.md (기계 단계, LLM 0회. 시드 URL을 헤드리스
+                       브라우저로 렌더해 텍스트를 남긴다 — SPA 문서는 WebFetch로 본문이
+                       오지 않는다, ADR-0061. 실패해도 파이프라인을 세우지 않는다)
   → [1. draft]     → topics/{slug}/script.md  (헤드리스 1회 — 시드 기사를 읽고 통짜 내레이션.
```

`specs/05-pipeline.md` 단계별 규칙에 `[0f]` 한 줄 추가 + `[1]` 입력 사다리 명시
(`seed-body.md` → WebFetch → WebSearch).

`specs/06-topic-research.md` 토픽 패키지 구조:

```diff
 topics/{slug}/
 ├── seed.md              # [0] 소재 한 줄 + 시드 기사 URL (+ 고른 이유 한 줄)
+├── seed-body.md         # [0f] 시드 기사 본문 텍스트 (헤드리스 렌더. 사람이 붙여넣어도 된다)
 ├── script.md            # [1] 대본 — 사람이 읽는 정본
```

`specs/06-topic-research.md` 소스 지위 표에 주석 한 줄: **렌더는 시드를 확보하는 수단일 뿐
지위를 바꾸지 않는다** — `seed-body.md`가 나무위키 본문이어도 `[2] factcheck`의 근거로는
여전히 못 쓴다.

`specs/06-topic-research.md` 시드 기준 4 개정 (사람 결정, 2026-08-24 — 이 ADR의 실측이 근거다):
**나무위키도 얇으면 시드가 아니다.** 기준 4는 "한국 소재는 나무위키를 먼저 본다"였는데,
먼저 보는 것과 두터운 것은 다른 조건이다. 이 ADR을 재면서 나온 값 — 석빙고 나무위키 문서의
본문은 **4,854자**(개요가 한 문장: "석빙고(石氷庫)는 얼음을 저장하기 위하여 만든 석조
창고를 말한다")이고, 같은 백로그의 쿠치사케온나는 **36,272자**다. 석빙고 편이 시드에서
문장을 못 얻은 이유는 렌더 실패만이 아니라 **문서가 얇았기 때문이기도 하다.** 그러므로
순서는 `나무위키 먼저 → 두터운지 본다 → 얇으면 위키백과 → 그것도 얇으면 소재를 미룬다`이고,
**두께가 순서를 이긴다.**

**비용**: 0. 설치된 브라우저, 토픽당 1회 2.4~61.5초(실측).

**되돌릴 조건**

1. 나무위키(또는 주요 시드 사이트)가 헤드리스를 차단해 본문이 안 오면 → 대안 1(사람 붙여넣기)로 강등. `seed-body.md` 계약은 그대로다
2. `[1]`이 렌더 텍스트의 내비게이션 목록(보물 1~200 등)을 본문 사실로 오인해 대본에 쓰면 → 대안 5(본문 추출기) 승격
3. 렌더가 되는데 본문이 비는 사이트(무한 스크롤·클릭 필요)가 나오면 → 대안 2(Playwright) 승격
4. `[0f]`가 돌기 시작한 뒤에도 `[2] factcheck`의 근거 URL에 시드 도메인이 한 번도 안 나오면
   → 시드가 여전히 대본에 안 닿는다는 뜻이다. 원인이 두께인지 렌더인지 다시 가른다
